《Palantir 13号员工：大模型是随机精灵，本体论是拴住它的桩》

Palantir 的软件拆成 550 个微服务，每个服务每天发布好几次。它的客户里有情报机构和军方，部署环境经常物理隔离，内网根本碰不到，潜艇只肯在指定的窗口升级软件。

2023年7月，这家公司的 CTO Shyam Sankar 上了投资人 Sarah Guo 和 Elad Gil 的播客 No Priors，聊 Palantir 押注 AI 的新平台 AIP。他是公司第13号员工、第一位商务侧员工，加入快二十年，此前以 COO 的角色长期管业务，如今是 CTO。

他的起点比大多数人曲折。人生头三年在尼日利亚度过，父亲在那里建起非洲大陆第一家制药厂，此前整个大陆的药都靠进口。后来因为暴力冲突，全家以难民身份逃到美国，在佛罗里达重新安家。他记得航天飞机发射时全校跑到操场看，周六早上六点偶尔被双音爆震醒，至今还在等商业航天把太空时代带回来。2003年他到了硅谷，进的第一家公司是做国际汇款的 Xoom，创始人是 Kevin Hartz，Peter Thiel 也是种子投资人。三年后，他加入 Palantir。

打动他的有私人原因：叔叔是恐怖袭击的受害者，9·11 那天他本人就在纽约。

我宁愿在这么重要的问题上失败，也不想去做别的任何事。

前置部署工程师：服务员得待在厨房里

加入时公司连产品都没有，这位商务侧员工先写了个候选人管理系统，又客串激进的 QA 测试员。真正立住的贡献，是他建起来的「前置部署工程」（forward deployed engineering）团队。

点子来自 CEO Alex Karp 的一个观察：法国餐厅为什么好吃？一种解释是，那里的服务员本身就属于厨房，对每道菜有足够深的理解。Palantir 把这个逻辑搬进软件行业：派到客户现场跟人打交道的得是计算机科学家，他们清楚产品今天能干什么、在什么条件下能跑通，一个人同时干产品经理、客户成功和工程师三份活。

这套方法背后藏着一把狠尺子：评判标准从「软件符不符合规格」换成「客户的处境今天有没有变好」。规格不重要，昨天的雄心也不重要，重要的是明天还能多做多少。政府客户的动机也天然强，他形容自己得使劲穿客户的鞋多走几里路，活干没干好看客户的状态，填完表格根本不算数。

还有更现实的算计。早期做政府客户，整个技术栈里任何一环掉链子，交付就完不成。那时 AWS 还没影，没有现成云可以依赖，一家公司想在这种环境里活下来，对「自己必须亲手搞定什么」的估计就得非常激进。

Gotham、Foundry、Apollo：三块地基

聊 AIP 之前得先弄清老本行，Palantir 原本有三块平台：

  • Gotham，旗舰政府产品，服务情报和国防客户，围绕杀伤链工作：怎么从发现目标走到对目标产生效果。
  • Foundry，通用数据集成平台，处理结构化和非结构化数据，把数据当代码对待，最后汇进一个本体（ontology）：语义层里既建模企业里的名词，也就是概念，也建模动词，也就是动作。
  • Apollo，最初为自己造的部署系统，把软件送进各种刁钻环境，被他们称作 CI/CD 的后继者：自主的软件交付与部署。

Foundry 的本体层值得多说两句。Sankar 的说法是，仪表盘只给你可见性，Foundry 给你的是能点下去就改东西的像素：想调配库存，平台得能写回 SAP，能读写你的交易系统，去编排整个企业。业界爱说的数字孪生，指的大概就是这种东西：对业务有个概念模型，还能拿它去影响决策。客户可以把企业看成一张链起来的决策网，做反事实推演：这么改会发生什么？美国和英国的新冠疫苗分发跑在这套平台上，商业公司应对供应链危机用的也是它。

Apollo 解决的问题更具体：550 个微服务要独立升级，有的环境不联网，有的潜艇只肯在特定窗口升级，那就把软件和部署环境分开建模，交给系统去编排蓝绿升级、健康检查、前进回滚，还要跟 CVE 漏洞库联动，决定什么时候召回或屏蔽某个版本。这套东西最近吃香了，欧洲客户要主权 SaaS，SaaS 公司要进客户的 VPC，一千个客户环境怎么管，Apollo 就是答案。

扩张路径也有意思。公司创立就是为了服务情报和国防，2010、2011 年才有第一个商业客户，用 Sankar 的话说，扩得相当不情愿。

得靠詹姆斯·邦德这么性感的东西，才能说服工程师去干数据集成这么无聊的活。

流行的看法是数据集成无聊且已被解决，他的判断相反：这是个无聊且远没被解决的问题，所有人都在拿胶带到处糊。把它产品化，市场才真正打开。

AIP：给随机精灵造工具工厂

2022年第四季度，Palantir 决定重注大模型。Sankar 回忆，当时最兴奋的点在于，LLM 好像就在等本体这个东西。过去二十年他们反复琢磨动态本体怎么建模、对人为什么有价值，结果发现本体提供的语义层能把信息高度压缩进上下文窗口，让基于 LLM 的函数变得可靠。

他管大模型叫随机精灵（stochastic genie）。这东西更像统计学，很多工程师却拿微积分的直觉去套，结果它灵的时候像魔法，不灵的时候直接跳崖。正确的姿势是承认它随机，围绕这个前提搭整套工具链。他自己列了几件：

  • 用评测（eval）取代单元测试的思路：一个 LLM 函数要跑多少次，你才敢信它会照你想的做？
  • 遥测和日志：多久看一次 trace，甚至可以对 trace 写单元测试，算一种健康检查。
  • 用例校准：最好的用例是模型做对了收益巨大，做错了等于什么都没发生的那种。

AIP 是一整套核心技术，把 LLM 驱动的体验带进客户的私有网络和私有数据，Sankar 称它为一座应用锻造厂。他强调 LLM 需要工具，插件这个词不够准，工具更贴切，客户需要的还不止一个工具台，而是一座工具工厂。大模型本身不懂轨道仿真，也算不准30天后的库存，配上对的工具，这些它都能干得相当好。

因为 Foundry 打好了地基，客户几周内就能造出嵌进现有决策界面的副驾（copilot），比如调配库存、判定车险理赔。他早上刚看了一个 demo，帮一家大型车企管理质量成本：聚类索赔文本，找出供应链里哪个供应商的哪个子部件在磨损，提前识别召回的前兆，把保修和召回的成本压下来。

模型本身在商品化，开源越来越多，价值往哪去？Sankar 把模型比作「有点疯的天才」，单个专家会犯错，那就让一组疯狂天才互相对照。主持人接话说想要一支疯狂天才合奏团，他认可这是正确方向，还补了一句：模型公司很难这么干，它们要「一个模型统治一切」，企业要的是集成。如果输出是 JSON 或 DSL，解析共识和分歧都容易，这才真正把模型当统计学对待，UI 也得跟着按统计学的思路设计。

聊天是最低效的入口

他举了个夏威夷的例子。美军要从一个城市撤离非战斗人员，作战计划（O 计划）文档里写清了资源类型、阶段、时间线、风险和假设。用户输入一句「给我生成撤离行动方案」，回来的东西是一张带资源配置的地图、一份资源矩阵和资源调拨单，点一下确认，方案就活了。

这背后是他对交互的判断：聊天是严重受限的界面，往极限里说，提示词是给开发者的东西。他也承认现实没那么整齐，有些提示词会漏到用户手里，用户有时也确实想聊天，很多人从聊天框起步，毕竟 ChatGPT 太火了。但理想形态是，用户带着意图进来，系统把应用状态和意图合并，输出一个新的应用状态。输出别停在一段话上，直接给一段 JSON 或 DSL，去操纵应用层。推到极致，他甚至反问：还要 UI 干什么？如果数据 API 和本体把数据建模得足够好，LLM 可以直接生成终端用户想要的体验。

内部有个例子佐证：一个原本排上路线图、预估两个人做两个月的 feature，一个工程师几个小时就做出来了，因为其中大部分工作量其实是 UI。把 UI 换成语言，整个等式就变了。今天有哪些 UI 你根本不必再建，值得每个团队重新算一遍。

这会动摇一批公司的护城河。主持人 Sarah Guo 提到，SAP、Workday 这类系统的一部分壁垒，恰恰来自动辄六个月的实施和集成。Sankar 补了两个观察。一是加州大学伯克利分校的 Gorilla 论文证明，微调后的 LLM 能可靠地告诉你该调哪个 API、传什么参数，那系统集成的形态就要变，真正打通的统一界面会变得可行。二是波音和海军还在为 F-18 大黄蜂的数据权扯皮，未来可能是另一番景象：政府手里握着 F-18 生产设计的 LLM，交机时连模型一起交付，维护、换部件、重新集成这些过去被专家知识锁死的事，都变得可查询。企业里换掉 Workday 会不会崩、牵连什么，同理。

智能体：一次只放行一个状态转移

聊到 agent 这个词，Sankar 说他几乎不敢用，因为流行含义跑偏了：大家默认 agent 要自己想出一个任意的计划，把自主规划当卖点。企业的现实是，那里本来就有一套或明或暗的状态机，规定了什么状态能变、什么不能动。靠谱的做法是给 agent 一小段状态机的上下文，讲清它的权限和护栏，起步只给它一个状态转移的权限，就一个。再把一个个转移串起来，驱动真正的自动化。

如果做的是代码副驾，这个公式很直观，应用状态加意图，生成一段代码；业务流程复杂一点，就需要一点提示和引导，分寸感是门手艺。这样设计还有个好处：每个状态转移背后本来就有个人对它负责，人机团队自然长出来，一线员工升格成 agent 的管理者。从变革管理的角度看足够安全，产生的日志又能反过来证明这套东西真有价值。他的类比是，这条路更像特斯拉做自动驾驶，每天多拿到一点自动驾驶能力，跟 Cruise 那种全有或全无的孤注一掷正好相反。

为了让工程师建立手感，Palantir 把实验当成了组织级任务：给自己的事故响应流程造副驾，先解决自己的问题，才能摸清它哪里惊艳、哪里跳崖。另一个细节是，涉密环境用不上 GPT-4，只能靠开源模型，所以内部的 ChatGPT 同时跑着多个模型，工程师对比输出、耗时、token 数，归纳地摸索每个模型的能力边界。

医疗占三分之一：警报收件箱该换成方案收件箱

CEO Alex Karp 放过一句豪言，Palantir 要拿下 AI 的全部市场份额。Sankar 的解释很直接：该做的预习做完了，保护数据、把 LLM 带进私有网络、投入运营，三件事的平台都现成。

他拿数据行业的旧剧本作比：当年人人都有个数据创新实验室，现在换个名字叫生成式 AI 创新实验室，结构一模一样。他的建议是，用例没变，去年最重要的业务问题今年还是那些，把新技术直接压上去。决策网里没有孤立决策，上游的选择影响下游，把这些连起来，反而缩小了交给 LLM 的问题的难度，部署还能增量推进，形成复利。他判断，价值最终会沉淀到拥有应用层的人和企业手里，Palantir 会往这里猛攻。

医疗大约占 Palantir 业务的三分之一，是增长最快的板块之一，客户包括英国 NHS 和美国多家医院系统，去年还跟克利夫兰诊所签了十年合作。Sankar 把医疗拆成两层。运营层跟管理任何机构没区别，供、需、人力，典型形态是一只警报收件箱：异常堆积如山，人先排优先级再处理。AIP 想做的是把「给人看警报」升级成「给人看方案」：模型给出建议和一个预演好的场景，人只需要批准或拒绝。这里的关键原语是场景，像 Git 里的分支，一组暂存的修改，没有这个原语，每个客户都得重造一遍。

临床层的目标是减少人的苦活。他没想让 LLM 决定病人该怎么治，那是医生的领地，要压缩的是翻病历、跑流程这类事务性工作，把原来耗掉的人力时间变成 400 毫秒的事，让诊疗现场的信息更完整。他还提到一个管理者视角的用法：不问模型「帮我处理这条理赔」，而是问「我这个状态机哪里有问题」，让它做结构分析，找出流程里的死循环。运营和分析就这么分了工：运营场景可以更激进，直接给推荐动作让人批准；分析场景里模型做诊断，没有魔法按钮可按。

这套逻辑里藏着一个排序变化。过去人处理警报要算账：值不值得为这条警报投入人力？当 LLM 能把所有警报都处理成待批的方案，排序的依据就从警报的严重程度，换成了解决方案可能带来的后果，而且你终于有机会把队列清空。

整期节目听下来，有三件事明天就能搬回自己团队用：

  • 先找「对了大赚、错了无损」的用例试水，这是 Sankar 给的校准标准，也是判断该不该把 LLM 接进某个流程的第一道闸。
  • 把评测当一等公民。别问它准不准，问它要跑多少次我才敢信，并对生产环境的 trace 持续做健康检查。
  • 少做聊天框，多画状态机。挑一个最安全的状态转移，给模型配好工具和护栏，让它输出结构化的修改，别只给一段话，人只负责批准。

Sankar 在节目里反复回到同一个姿势：从客户的问题倒着推，做出来的东西跟从技术正着推完全是两码事。Palantir 二十年攒下的家底，说穿了是一套「怎么让软件在真实世界的烂摊子里产生价值」的方法论，大模型来了，只是让这套方法论突然变得贵重起来。
