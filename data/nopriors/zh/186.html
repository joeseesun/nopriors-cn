《同时登上 IT 团队“最花钱”和“最讨厌”清单的公司，有人来换了》

Jake Stauch 在 Verkada 卖企业物理安全产品的那几年，养成一个习惯：跟 IT 团队开会时问两个问题，你们最花钱的地方是什么，你们最讨厌的东西是什么。

ServiceNow 经常同时出现在两份答案里。

这个细节听起来像销售段子，但它解释了一件事：一家 2024 年初才成立、在联合创始人 Alex 家客厅里起步的公司，为什么敢在第一天就把 ServiceNow 的名字圈在纸上，说我们要打败它。两年半后，这家叫 Serval 的公司有 200 名员工，Fox Corporation 全公司换上了它的系统。

Jake 在 No Priors 这期节目里，把这套打法的来龙去脉讲得相当直白。主持人 Sarah Guo 和 Elad Gil 追问了很多细节：怎么选赛道、怎么处理企业权限、怎么组织一个没有产品部门的工程团队。

一个被问出来的赛道

ServiceNow 是什么，用过的人都知道。它本质上是一个工作流自动化平台，可定制、可配置、足够强大，能把企业里五花八门的流程映射进去。IT 服务管理、工单、审批、资产，都跑在上面。

问题出在实施速度上。Jake 的描述很具体：你在平台上每冒出一个新想法，都得有人去实现，很多时候还得请咨询公司来实施，于是你的系统永远落后于你想要的状态 6 到 12 个月。

如果要做的是一个用五到十年的大流程，比如整条入职链路，业务本身不会怎么变，那前期投入这些实施成本是划算的，上线后能稳定跑很久。麻烦在于那些需要持续跟进的自动化：业务在变，需求在变，工具跟不上。

“它跟不上我想去的方向，而且一年比一年贵。这两件事叠在一起，就是大部分不满的来源。”

Jake 在 Verkada 待了很多年，一直在跟 IT 团队打交道，问他们该造什么。他很早就意识到这个品类里也许有更好的解法，但同样清楚，在很长一段时间里，看不出怎么才能赢 ServiceNow。对方是一家做得非常好的公司。

代码是自动化的正确表达方式

转折点来自一个技术判断，而非商业判断。

Jake 和 Alex 的共识是：代码才是企业里表达自动化的正确方式。那些拖拽式的工作流构建器，处在一个尴尬的中间层，对非技术用户来说太复杂，对技术用户来说又抽象得让人难受。

难点显而易见，会写代码的人不多，写到自己能用来做自动化的速度就更少。所以这个想法在很长时间里只是想法。

AI 把这个前提拆掉了。如果代码是正确表达方式，而现在任何人都能写代码，那就可以造一个更好的自动化平台。再往下推一步：自动化平台最好的市场在哪里？答案是去替代那些巨大的传统软件公司。

2024 年初开始动手时，coding agent 还停留在补全代码的水平，经常不管用。Jake 承认这一点，也承认这是一场押注。

他押注的理由是：编程是一个可验证的领域，这类能力应该能爬得比较稳。他没指望模型在通用软件开发上强到今天这个程度，但“重置密码、拿到审批”这类确定性流程脚本，定义清楚、结果可验证，模型迟早能做好。

早期的做法很土。每次演示前，他们先用提示词给模型塞一堆示例，告诉它“这里有一个重置密码工作流的建议写法”，然后靠不断扩充这个示例库撑着。后来模型自己变强了，强到什么程度？Jake 的说法是：只要 API 存在，你已经很难给出一条它自动化不了的工作流。

为什么不去做巨头的插件

企业软件创业有两条常规路径。

第一条是在巨头上面加一层薄薄的插件，跟现存者和平共处，等站稳了再往下扎。这条路成功率极低，Jake 只想到一个反向整合成功的例子：Veeva 从 Salesforce 上起步，后来长成了自己的平台。

第二条是往下打，先服务中小客户，做出规模再往上走。Salesforce 的挑战者、Workday 的挑战者大多这么干，HubSpot 前十年就是这么过来的。

Serval 两条都没选。他们在客厅里列了一张公司清单，圈出 ServiceNow，说要做成史上最大的企业软件公司。Jake 自己的说法带着自嘲：一切都在我们极度妄想的计划之中。

这个选择的价值不在口号，在决策。Jake 说得很清楚：如果从第一天就为大企业设计，所有产品决策、团队搭建方式、增长思路都会完全不同。先做小客户再往上爬，很多底层选择会在后面变成负债。

为什么不选 Salesforce 那类公司？Jake 的回答很诚实：他们想不出怎么赢，也想不出 AI 在这里解锁了什么对方追不上的东西。而在 ServiceNow 这个品类里，他们因为常年跟 IT 团队泡在一起，知道它的底层是工作流自动化平台，也知道代码生成正好能掀掉这个底座。

企业不缺智能，缺边界

节目里 Elad Gil 问了一个很多人关心的问题：OpenAI 的 Dot 这类个人助理型 agent，跟 Serval 是什么关系。

Jake 的回答是这期节目里最有信息量的部分之一。他说这类产品在消费者、中小企业、中端市场都很好用，但到了大企业会撞墙。

大企业里单个员工的权限窄得可怕。Jake 说他进场之前没真正体会到这一点：任何一个人的权限集都极其有限，很多公司甚至根本不允许你把个人 agent 带进工作环境。就算允许，它能干的事也少得可怜，连读你的邮件都勉强。你想动的那些系统、你想做的那些自动化，个人权限根本够不着。

Serval 的解法是绕开个人权限，走 IT 团队这条路。IT 手里有服务账号凭证和管理员级权限，可以做真正有权限做的事。代价是必须配一整套确定性流程：审批、审计轨迹、工单。

这套东西在 Serval 里是内建的，因为它底层本身就是一套工单系统。你说“我要让 agent 去做 X、Y、Z”，系统会生成访问请求，走审批，全程记录，通过之后给你一次性的即时访问权限，去跑那条确定性工作流。

Jake 承认这体验比消费级产品笨拙，但它是受监管的大企业采用这类技术的前提条件。

接下来是一个反直觉的判断。Jake 认为，模型越强、agent 能做的事越多，企业反而会把自己的权限收得更紧。

他的推理链条很朴素：今天我愿意给你多一点权限，是因为我判断你一个人搞不出多大破坏。可一旦你能调动一堆 agent，稍微超出常规的权限带来的潜在破坏就会被放大。网络安全领域已经在发生这件事。

所以大企业接下来会做的事，是把每个人的权限压到真正的最小值：除非这份工作必须，否则你不能读任何文档，也不能执行任何操作。但例外永远存在，天天都有。

“我们就是发放例外的这一层。你越收紧用户权限，我们就越重要。”

这里的分歧点值得单独说。市面上一批产品假设企业会越来越开放，让 agent 自由行动；Jake 的判断正相反，企业会越来越封闭，并且愿意为“如何安全地开一个口子”付钱。

把软件开发生命周期搬进 IT

Serval 最重要的产品原则，是把工程团队那套软件开发生命周期搬进 IT 部门。

Jake 强调，这在传统 IT 自动化里基本不存在。大部分新的 AI 产品也没打算做这件事，它们的做法是造几个 agent，直接推到生产环境。

一家大型金融机构不会在没有评审、没有用户验收测试的情况下上线新的 agent 能力。所以 Serval 里有开发环境、预发布环境、生产环境，有分支，有审批关卡，有完整的审计。IT 部门拿到的工具，和给软件工程师的工具是同一套。

但 Jake 强调另一件事：不能只丢一个 Cloud Code 过去说祝你好运。IT 人员的能力分布很宽，有人真的会写代码，也有人一辈子不想看见代码。产品要同时服务这两类人：代码永远可见，生命周期永远可走，但你可以选择不走那么深。

这里有一个我喜欢的细节，关于他们怎么决定什么进核心平台。

Serval 从不给客户做定制功能，一条都不做。Jake 说这个品类里也没人提这种要求。但他们在客户环境里观察到同一个自动化被反复搭建、反复改造时，会考虑把它变成产品的一级功能。

两个具体例子。很多客户在搭工作流，检测知识库里互相冲突或者已经过期的文章，于是 Serval 直接内建了这个能力。还有客户在搭自动化回收闲置的软件许可证，取消没人用的付费订阅，这个也被内建了。

他们还有一个专门给管理员用的 agent，叫 Catalyst。原因是第一代 AI 产品普遍有个坑：系统能搭得很复杂，然后你得花大量时间培训用户理解产品原语。Catalyst 干的事就是把对话里的需求直接翻译成平台里的原语，同时配置审批规则、权限检查、策略更新。

Jake 说这个 agent 现在就是产品的主界面。你不用先学会用 Serval，你跟一个懂 Serval 的 agent 说话就行。

Sarah Guo 在这里补了一个观察：这类交互其实在抬高大量用户的技术能力，把不是工程师的人往工程师的方向推。Jake 认同，还补了一个旧时代的痛点。传统自动化平台最劝退的问题是空白页：我知道我想自动化，但我不知道从哪开始。现在的产品可以反问你想从哪开始，然后给建议、解释概念、查资料，变成一个共建的伙伴。

SaaS 大灾变会发生，但不在系统记录层

Elad Gil 抛出那个流行说法：SaaS 大灾变，大家都能自己 vibe code 出内部软件，这些品类会消失。

Jake 的回应分两层，切得很干净。

第一层，系统记录类工具活得下去。他接触过所有尝试自己 vibe code 这类系统的公司，结论一致：企业软件本身就贵，建起来贵，维护起来更贵。除非需求极度特殊，自建在经济学上不划算。你会碰到一堆边缘情况，得有人维护，得配一个团队，然后你还要付这份人力成本，而且大多数人不愿意去内部工具团队干活。买现成的，这个买办决策到今天依然成立。

第二层，点解决方案和中间件会被吃掉。Jake 说很多公司有几百个 SaaS 应用，实际需要的大概就几十个。这波收缩会真实发生，被核心系统记录和核心平台吞掉。

他给出的结论很有分寸：大灾变会来，但发生在那些小市值点解决方案公司身上。ERP、HRIS、ITSM、CRM 这些系统记录会留下来，也许会变形态，同时会长出新一代的在位者。Serval 干的就是替代这批工具。

聊到钱的部分，Sarah 问企业客户在 token 花费上的态度变化。Jake 说 CIO 们确实在从早期的“token 随便烧”阶段往回收，但他认为总量还会继续涨，因为大多数公司才刚开始。客户真正要的东西是 ROI 证明，而非省钱。他们愿意短期收紧，长期还是准备加预算。

Jake 承认没人真正解决了“怎么衡量这些 token 换来了什么”。Serval 试过按工作流运行次数定价，理由是这更接近实际完成的工作量；按 token 计费衡量的更像是啰嗦程度和低效程度。

没有产品部门的 200 人公司

数字先摆出来。公司两年半，现在 200 人，今年 1 月是 20 人。

一年十倍的扩张速度，加上 Jake 说招聘还会加速。他的逻辑跟“AI 让公司变小”的流行叙事相反：每个员工确实比一年前能干多得多的活，但他们对每个员工的野心也变得更大，所以想要更多人，而非更少。

组织上最特别的一点是：Serval 没有产品部门。

产品决策被下放到了工程团队。原因是工程师天天泡在客户里。没被派驻现场的工程师也在客户的 Slack 频道里，大多数工程师每周至少参加一次客户电话，很多人每天都有。Jake 打的比方是 immersion 学外语：你彻底泡在买方和客户的思维方式里，能实时感知他们的偏好变化，他们试了什么新产品、对什么兴奋，工程团队全都知道。

代价也很清楚。产品发布和变化的速度，经常快到没人跟得上，包括 Jake 自己。他的应对是提高招聘标准，只要产品导向的工程师，因为大量决策必须在边缘完成，不可能每件事都往上报。

还有一条他特别自豪的能力：愿意往回撤。Serval 多次把过去投入很深、当时非常笃定的东西直接删掉，承认市场变了、客户变了，然后完全换一种做法。他把这种反复自我重写的能力，视为公司能跟上节奏的原因。

关于背景 agent，Jake 的判断值得记住。他称这是企业软件的终极登月计划：agent 自己跑出去，自动发现你的问题，自动解决你的问题。但没人真正做成了。

卡点在两难。你希望它足够自主，不用人盯着；自主在企业里又非常可怕。过去两年多次出现 agent 被给了一个任务，为了完成任务做出意料之外的动作。一个能力足够的 agent 理论上可以直接写代码，对你所有系统采取行动，这是一个没有边界的风险，短期内没人敢承担。

他给出的现实路径是渐进式提权。agent 跑出去做事，回来提要求：我想要这个能力、想调这个工具、想跑这个脚本，能不能批。人一条条批，配上权限和护栏。时间长了，agent 的工具箱足够大，能解决大部分问题，也就变得相当能干。这个过程很烦，要人盯着，但它是唯一可走的路。

Elad 追问这是模型能力问题还是护栏问题。Jake 说两者都有，记忆必须更好，上下文必须极长，他想要一个能追溯回第一次对话的单一会话，而非一堆割裂的聊天窗口。但权限问题会一直是最大的那个。

明天就能用的四件事

这期节目信息密度高，落到行动上，有几条是能直接拿走用的。

  • 找那个“最恨现有系统”的 IT 负责人，而非最懂 AI 的人。Jake 的整套打法是自上而下卖给 IT 领导层，再分发到 HR、财务、法务。找错第一个人，项目会卡在试用阶段。
  • 把第一次部署做成能写进对方晋升材料的案例。Serval 在 Fox 的落地案例里，一线主导迁移的人在内部被提名为全公司 MVP。Jake 的说法是，必须让客户相信用这个能升职，而不只是不出事。
  • 产品面向非工程师时，把审批、审计、环境隔离当成产品本身来做，别当合规成本。Jake 那句“边界就是产品”，值得抄进任何企业级 AI 产品的设计文档。
  • 计价和汇报口径往“完成了多少工作”靠，别停在 token。按工作流运行次数计费，按替代掉的人力或平台成本折算 ROI，CIO 们现在缺的正是这张账。

还有一条更长期的：如果你的产品假设企业会对 agent 越来越开放，可能要重新想一遍。Jake 赌的是相反方向，权限会越收越紧，价值和机会都集中在“谁能安全地发放例外”这件事上。
